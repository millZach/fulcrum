# M2: Concept-to-3D quality

> Status: Replay acceptance completed on 2026-08-24. Live-provider acceptance is pending separate, explicit authorization. No paid M2 run has happened.

## Outcome

M2 turns an approved concept set into a human-approved asset plan and a validated asset batch. It records why each asset exists, which approved concepts it descends from, what it depends on, how much quality work its class receives, and why Fulcrum kept or regenerated each 3D revision.

The replay implementation is accepted when one M2 brief passes through the reused creative front, plan approval, batch generation, deterministic inspection, semantic hero evaluation, a finding-directed change of views, and best-revision selection with identical binary artifacts and canonical lineage across two fresh runs.

The milestone's live proof remains open until Zach separately authorizes provider use and a positive budget. That run must exercise real planning, image, 3D, and vision providers without duplicate spend.

## Product boundary

M2 adds these capabilities to the approved M1 concept package:

1. Build an immutable, dependency-ordered asset plan from the approved Game Design Spec and concept set.
2. Classify planned assets as hero, kit, procedural, or functional.
3. Stop for human approval before any batch asset generation starts.
4. Generate cardinal concept views for eligible assets when the selected 3D provider profile accepts multiview input.
5. Inspect mesh, material, texture, and topology facts for every generated asset revision.
6. Render repeatable turntables and run semantic vision evaluation where class handling requires it.
7. Select a bounded regeneration strategy from recorded findings and retain the Pareto-best revision.
8. Show the plan graph, multiview inputs, quality gates, cited frames, and strategy history in Studio.

M2 reuses M1's interrogation, Game Design Spec, visual-direction, concept-plan, concept-generation, and concept-set approvals. An M2 project skips M1 sound planning after concept-set approval.

## Artifacts and lineage

| Artifact                                  | Purpose and lineage                                                                                                                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Approved Game Design Spec                 | Supplies the mechanics, camera, constraints, facts, and assumptions that planning must preserve.                                                                                                                   |
| Approved visual direction and concept set | Supplies the selected image revisions and inherited visual tokens. M2 accepts only the current revision and approval hashes.                                                                                       |
| Asset plan                                | Stores topologically ordered assets, class, rationale, dependencies, acceptance criteria, class handling, exact source refs, source hashes, and provenance. A change request creates one descendant plan revision. |
| Class quality policy                      | Records the concrete thresholds used for one classification. Deterministic and semantic reports cite its revision and hash.                                                                                        |
| Concept-view document                     | Stores one cardinal role, fixed camera guidance, compiled prompt, image, anchor concept, approved ancestors, attempt, provider metadata, and source hashes.                                                        |
| Multiview concept set                     | Packages the front, left, back, and right view refs accepted by the provider profile. A strategy-driven replacement cites the prior set and the `change-views` decision.                                           |
| Asset document                            | Stores the GLB, provider and model, source concept, source image hashes, generation claims, cost, and external job ID. Regenerated documents also cite their parent asset and strategy revision.                   |
| Deterministic report                      | Stores measurements, gates, findings, pass state, quality vector, asset hash, classification, and policy lineage.                                                                                                  |
| Turntable manifest                        | Stores renderer version, camera configuration, source GLB hash, and four to eight immutable PNG frame refs according to class policy.                                                                              |
| Semantic report                           | Stores the exact asset and turntable lineage, rubric version, request digest, provider metadata, verdict, dimension scores, and findings that cite frame artifacts and optional normalized crops.                  |
| Regeneration decision                     | Stores source report revisions, best-known asset revision, rationale, finding IDs, and one typed strategy.                                                                                                         |
| Asset batch checkpoint                    | Stores each asset's current and best refs, attempt count, validation state, final reports, latest decision, and multiview set. It is project state made only of immutable refs.                                    |
| Workflow events and submissions           | Record node checkpoints, approvals, provider intents, completions, suspensions, strategy selection, and best-revision comparisons. Event reads use row order to break timestamp ties.                              |

Repository artifact bytes are content-addressed. Revisions are append-only. Project and workflow state carry refs rather than image, GLB, or turntable bytes.

## Approval points

M2 has four high-leverage approvals:

1. **Game design.** The resolved Game Design Spec must be approved before direction work.
2. **Visual direction.** One direction and Visual Bible must be approved before concept planning.
3. **Concept set.** Every required concept slot must have an explicitly kept revision. Approval sends M2 directly to asset planning and does not start sound work.
4. **Asset plan.** Studio shows class lanes, dependency arrows, source lineage, criteria, and handling. Approval binds the exact plan revision and SHA-256 before the graph can enter `asset-batch`.

An asset-plan change request requires notes and permits one replan. A second request blocks at the replan limit. Rejection blocks the project. M2 does not ask for a separate human approval on every generated asset; deterministic and semantic policies decide batch validation.

## Per-class handling

The approved plan stores this versioned handling table:

| Class      | Planned production route | Concept views          | Deterministic QA  | Semantic QA | Regeneration handling | Plan limit      |
| ---------- | ------------------------ | ---------------------- | ----------------- | ----------- | --------------------- | --------------- |
| Hero       | Provider 3D              | Multiview if supported | Full              | Turntable   | Finding-directed      | 2 regenerations |
| Kit        | Provider 3D              | Single view            | Standard          | None        | Finding-directed      | 1 regeneration  |
| Procedural | Parameterized generation | None                   | Procedural output | None        | Parameter adjustment  | 2 regenerations |
| Functional | Runtime authored         | None                   | Gameplay function | None        | Implementation repair | 1 regeneration  |

Classification currently changes multiview eligibility, semantic routing, mesh and material thresholds, texture expectations, topology limits, turntable size and frame count, and allowed regeneration strategies. Hero policy renders eight frames and permits semantic evaluation. Kit renders six frames. Procedural and functional render four frames and skip semantic evaluation.

The production-route labels for procedural and functional assets are persisted planning intent, not dedicated adapters yet. The current batch implementation sends every class through `AssetProduction` with an approved concept anchor. Dedicated parameterized and runtime-authored producers remain future work. The runtime quality policy counts total attempts, including the initial attempt, while the plan table describes regeneration count. Hero and kit express the same effective bound under those two conventions. Procedural and functional repair routing is not yet implemented beyond their distinct QA policies.

## Studio experience

`?studio=m2` mounts the M2 flow inside the shared creative shell.

- `AssetPlanView` presents the dependency SVG by class lane, shows plan hash and provenance, and exposes approve, request changes, and reject actions.
- `MultiviewConceptStrip` shows generated cardinal views and their role, prompt, model, and lineage details.
- `QualityEvidencePanel` groups deterministic gates by mesh, material, texture, and topology. It also shows turntable frames, crop overlays for cited findings, semantic verdicts, current and best revisions, and the regeneration timeline.
- The completion view lists every batch asset and marks its validation state before opening its evidence.

The Studio client calls `POST /api/projects/:projectId/approvals/asset-plan`. Snapshot mapping resolves stored report refs into the evidence required by these views.

## Provider, cost, and recovery policy

### Replay

- Asset planning uses a deterministic local derivation and produces hero, kit, procedural, and functional entries.
- Concept views use a deterministic raster renderer through the same durable image seam as live work.
- Asset production uses the replay adapter and deterministic GLBs. Replay pins the Meshy profile to `meshy-7` and the Tripo profile to `v2.5-20250123`, regardless of live model environment variables.
- Turntables use the software rasterizer. Semantic evaluation reads exact request digests from the replay vision catalog.
- Replay records submission intents and events but spends $0.

### Live

- Asset planning uses the configured structured orchestrator provider. An OpenAI API route reserves the configured text amount before its call.
- M1 concepts and M2 concept views use the signed-in subscription image runner. The image seam stores intent first, applies retry and elapsed-time limits, and marks an interrupted live call as unknown instead of repeating it.
- Asset production supports Meshy and Tripo. Meshy `meshy-7` and Tripo `v2.5-20250123` declare multiview capability. Other configured model versions fall back to single-image generation, and `change-views` cannot be selected when the real adapter profile rejects multiview.
- Meshy and Tripo reserve configured amounts against the project budget before provider submission. Their request fingerprints include ordered image hashes, model version, generation options, parent asset hash, and strategy hash.
- Semantic evaluation prefers an available signed-in vision route, then an OpenAI API route. API vision reserves its configured amount before evaluation.

Every external operation records a durable intent and idempotency key. A ready submission resolves its stored revision. A pending provider job is inspected rather than submitted again. A live interruption after a call may have started becomes `submission-unknown` and requires user action. The macro graph records checkpoints and reconstructs after restart. Best selection compares hard-gate, critical, major, minor, and semantic dimensions; a regression cannot replace the Pareto incumbent.

No paid M2 path has been run. Live cost, elapsed time, provider output quality, and end-to-end recovery remain unmeasured acceptance evidence.

## Current implementation boundaries

- The dependency graph is topologically ordered for review and batch input. The current bounded `foreach` can start independent and dependent entries within the same concurrency window; dependency edges are not job-readiness locks.
- Procedural and functional route names do not yet dispatch to dedicated generators.
- Only classes whose handling requests semantic QA receive vision judgment. In the shipped table, that is hero only.
- The replay vision catalog proves known request digests. It does not estimate how often a live model will produce the same verdict.
- A batch completes automatically after policy validation and a validated hero. There is no final batch approval gate.

## Non-goals

M2 does not include:

- Blender repair, rigging, animation, or a general geometry-edit operation library
- Scene composition, environment assembly, gameplay implementation, or a playable vertical slice
- Open-ended autonomous refinement, oscillation detection, or the later Gauntlet
- Dedicated procedural environment and runtime gameplay-volume adapters
- Human approval for each asset attempt or semantic verdict
- New remote artifact storage, collaboration, or provider marketplace work
- A claim that the unrun live path has passed product acceptance

## Implementation sequence

Each landed slice kept the existing replay paths green.

1. **S1, macro graph.** Moved the post-concept tail onto named Mastra nodes with suspend and resume behavior, checkpoint events, bounded `foreach`, M0 parity, and M2 slot adapters.

4. **S4, multiview.** Added capability profiles, cardinal concept-view generation through the durable image seam, Meshy and Tripo multi-image requests, replay twins, and `change-views` fulfillment.
5. **S5, Studio.** Added M2 routing, the asset-plan graph and approval view, multiview strip, per-asset quality evidence, turntable crops, and the strategy timeline.

Two post-S5 fixes scoped semantic submissions by asset and moved model plus multiview capability resolution into one shared profile. S6 added this contract, the fresh-run replay acceptance, and determinism fixes for preview seeds, asset-plan provenance order, and evidence order. A post-S6 review pass made at-cap acceptance require a passing semantic verdict, capability-gated `change-prompt`, scoped semantic reuse by request while keeping the replay catalog content-addressed, and sealed the remaining boundary casts, capability contracts, and cross-project approval gaps.
