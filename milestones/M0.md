# M0 — Real Walking Skeleton

## Objective

Prove that Fulcrum can carry one immutable creative lineage through model-backed creative development, reviewable concept production, human approval, real image-to-3D generation, deterministic asset validation, and a rendered Three.js scene.

M0 is complete only after one live run produces real files through real external providers. Replay adapters are required for automated tests but do not satisfy completion.

## Fixture brief

M0 ships with one reproducible fixture while still allowing a custom brief:

> Create a stylized third-person fantasy extraction arena centered on an ancient stone reliquary. The reliquary is a squat, readable hero prop made from weathered dark stone, restrained bronze bands, and a cyan crystal core. The visual language is painterly and hand-sculpted rather than photoreal. The arena should make the reliquary feel important, mysterious, and visible from across the play space.

Only the reliquary is generated as a 3D asset in M0. The surrounding review scene uses deterministic runtime geometry, lighting, and ground treatment so the generated asset remains the object under test.

## Live provider path

The first supported path is:

- A signed-in Claude Code, Codex, Grok Build, or OpenCode subscription client for the structured creative revision, with the OpenAI API as the automatic fallback when the OpenAI subscription is unavailable
- An independently selected implementation provider, persisted for later milestones but not invoked by M0
- An optional image route: Codex ImageGen with GPT Image 2 through the OpenAI subscription by default, the GPT Image 2 API as fallback, an OpenAI-compatible custom API, or Fulcrum's procedural concept renderer
- Meshy Image to 3D for the default textured 3D asset path; the model version is explicit runtime configuration
- Tripo `image_to_model` as a selectable alternate adapter
- Local deterministic GLB inspection
- Three.js for the browser review scene

Provider aliases and exact versions are recorded in provenance. They are not embedded in domain schemas.

Required runtime configuration:

```text
# Leave provider overrides unset for OpenAI subscription -> API fallback.
# FULCRUM_ORCHESTRATOR_PROVIDER=openai
# FULCRUM_IMPLEMENTATION_PROVIDER=openai
# FULCRUM_IMAGE_PROVIDER=openai-subscription

OPENAI_API_KEY=              # required by the OpenAI API execution fallback
# FULCRUM_OPENAI_API_MODEL=gpt-5.6-terra  # optional model override

MESHY_API_KEY
FULCRUM_MESHY_MODEL=meshy-6

FULCRUM_M0_BUDGET_USD
```

A live run cannot start if the selected orchestrator or image provider is unavailable, the selected external providers are not configured, or a positive budget is missing. Fulcrum prefers a signed-in OpenAI subscription for orchestration and Codex ImageGen, then selects the matching OpenAI API route when a subscription capability is unavailable. The API fallback requires `OPENAI_API_KEY`; its balanced text model can be overridden explicitly. Subscription credentials stay in their owning clients. API credentials are never persisted in project state or logs. A custom image API has its own optional configuration.

Provider references:

- [OpenAI GPT Image 2](https://developers.openai.com/api/docs/models/gpt-image-2)
- [Claude Code setup and subscription sign-in](https://docs.anthropic.com/en/docs/claude-code/getting-started)
- [Codex non-interactive execution](https://github.com/openai/codex/blob/main/codex-rs/README.md)
- [Grok Build headless execution](https://docs.x.ai/build/cli/headless-scripting)
- [OpenCode non-interactive execution](https://opencode.ai/docs/cli/)
- [Meshy Image to 3D](https://docs.meshy.ai/en/api/image-to-3d)
- [Tripo image-to-model generation](https://platform.tripo3d.ai/docs/generation)

## Required user journey

1. The user starts Fulcrum locally, reviews the automatically selected orchestrator and future implementation providers, selects the optional image route and 3D provider, then creates a project from the fixture or a custom brief.
2. Creative Development produces a compact Game Design Digest and structured Visual Bible.
3. Concept Production creates one isolated, full-object reliquary concept suitable for image-to-3D.
4. The Studio shows the concept, creative constraints, provenance, estimated or actual cost, and approval controls.
5. The user approves the exact concept revision or requests one replacement.
6. Asset Production creates one Fulcrum submission with the selected Meshy or Tripo adapter, records the external job, and safely resumes while it is pending. An ambiguous submission is never automatically duplicated.
7. Fulcrum downloads the resulting GLB into the artifact store and records its content hash and lineage.
8. Asset Quality parses the file and records deterministic measurements and gates.
9. Scene Authoring produces a Fulcrum Scene Spec containing the reliquary, ground, lighting, and camera.
10. Runtime Builder renders the scene in the browser and captures a review image.
11. The user approves or rejects the visual slice.
12. Fulcrum records the terminal M0 result and leaves all artifacts inspectable.

## Human approvals

M0 has exactly two required approval suspensions:

1. **Visual-direction approval:** approves the Visual Bible and one concept revision together.
2. **Visual-slice approval:** approves the rendered scene revision.

The user may request one concept replacement before approval. No other normal decision interrupts the run.

## Asset acceptance policy

The M0 reliquary must satisfy:

- GLB parses without errors.
- At least one mesh primitive is present.
- Vertex and triangle counts are measurable.
- Bounding dimensions are finite, non-zero, and normalizable to the authored target size.
- At least one material is present.
- Referenced textures are present or embedded when the provider claims a textured result.
- Scene load produces no uncaught runtime or console errors.
- The artifact hash, byte length, provider job ID, source concept revision, and run ID are recorded.

Polygon count and texture resolution are reported but are not hard quality gates until a real output establishes a reasonable baseline.

## Bounded failure policy

- Concept generation: one initial attempt and at most one user-requested replacement.
- Asset generation: one initial external job and at most one regeneration after a deterministic terminal failure.
- Polling and download retries do not create new generation jobs.
- Every retry checks remaining cost and elapsed-time budgets.
- Authentication, missing configuration, rights acknowledgement, and exhausted budget require user action and never retry automatically.
- A rejected final slice ends M0 as a valid rejected result; it does not enter an autonomous refinement loop.

## Acceptance criteria

### Product

- [ ] One command starts the Studio and orchestrator from a fresh configured checkout.
- [ ] A project can be created from the fixture brief.
- [ ] The Visual Bible and concept appear in the Studio.
- [ ] Approval targets an immutable revision and hash.
- [ ] A concept image is stored locally with provenance for the selected procedural or external image route.
- [ ] A real image-to-3D job produces a local GLB.
- [ ] Deterministic measurements and gate results are visible.
- [ ] The GLB appears in the Three.js review scene.
- [ ] A review render is stored and can be approved or rejected.

### Durability

- [ ] Restarting during either approval resumes the same run.
- [ ] Restarting while the 3D job is pending reconciles the existing provider job.
- [ ] A simulated crash during ambiguous submission blocks safely instead of automatically spending again.
- [ ] Repeating a completed node returns the existing revision instead of duplicating artifacts or provider spend.
- [ ] Project state can be reconstructed without reading conversational history or Mastra snapshots.

### Quality and safety

- [ ] Ordinary tests run offline through deterministic replay adapters.
- [ ] The live smoke test is explicit, budget-capped, and excluded from ordinary CI.
- [ ] Secrets are absent from the database, artifacts, and logs.
- [ ] All generated artifacts have content hashes and provenance manifests.
- [ ] No workflow snapshot contains image or mesh bytes.
- [ ] No placeholder node claims that unimplemented production occurred.

## Non-goals

M0 does not include:

- Multiple concept directions or multiview generation
- Generated characters, enemies, rigs, or animations
- Modular architecture-kit generation
- Blender refinement
- Procedural environment dressing beyond the deterministic review scene
- Gameplay, combat, navigation, UI, audio, or VFX
- Automated visual improvement
- Gameplay or technical Gauntlets
- Godot, Unity, or Unreal adapters
- Deployment or multi-user collaboration
- A generalized runtime adapter registry
- A claim that the output is a fun game

## Implementation sequence

Each slice must leave the repository runnable and tested.

1. **Workspace foundation** — pnpm workspace, TypeScript configuration, Studio shell, orchestrator shell, and checks.
2. **Project truth** — schemas, SQLite project repository, filesystem artifact store, event log, revisions, and hashes.
3. **Creative revision** — brief ingestion, Game Design Digest, Visual Bible, and deterministic schema validation.
4. **Concept production** — Codex ImageGen subscription, GPT Image 2 API, procedural, and custom image adapters; artifact persistence; provenance; replay adapter; and Studio preview.
5. **Approval suspension** — immutable approval command, Mastra suspend/resume, and invalidation behavior.
6. **Asset production** — Meshy and Tripo submissions behind one interface, job journal, polling reconciliation, download, and replay adapter.
7. **Asset quality** — GLB parsing, measurements, gates, and Studio presentation.
8. **Scene and runtime** — Scene Spec v0, Three.js builder, browser preview, and review render.
9. **Recovery proof** — restart tests, idempotency tests, budget enforcement, secret scan, and one live recorded run.

## Exit artifacts

M0 ends with:

- A versioned creative revision
- An approved concept image
- One generated and validated reliquary GLB
- One Scene Spec revision
- One browser build and review render
- Two immutable approval decisions
- A complete provenance chain and event log
- A captured, rights-safe replay fixture for offline tests
- A short M0 report containing cost, elapsed time, failures, and accepted limitations
