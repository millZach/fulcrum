# M1 — Creative-to-Concept Generalization

> Status: Approved for implementation on 2026-08-18. Live provider spend still requires separate, explicit authorization.

Plain-English companion: [M1 product overview](../docs/m1-product-overview.html).

## Outcome

M1 turns materially different game briefs into approved game-design intent, a chosen visual direction, and a coherent concept set. The user should no longer need to repair hidden assumptions or manually carry visual language between prompts.

M1 is complete when varied briefs work through the generalized creative flow, one explicitly authorized live run reaches an approved concept set, and the M0 replay path remains green.

## Product boundary

M1 adds the six capabilities promised by the roadmap:

1. Accept varied game briefs.
2. Use Grill Me With Docs until Fulcrum and the user share a complete understanding of the project.
3. Offer multiple purposeful visual directions.
4. Support a focused direction change and independent concept regeneration.
5. Expand the Visual Bible into reusable structured visual tokens.
6. Prove that concepts inherit approved creative direction without manual prompt rewriting.

M1 does not deepen 3D generation or build a playable game. It reuses M0's providers, persistence, approvals, budgets, and recovery behavior.

## Grill Me With Docs

M1 uses **Grill Me With Docs**, whose package identifier is `grill-with-docs`. It runs `grilling` with `domain-modeling` as an internal Fulcrum capability.

### Background provisioning

- Fulcrum ships or pins `grill-with-docs`, `grilling`, and `domain-modeling` as part of its execution environment.
- Starting a project provisions and verifies the skill chain in the background before interrogation.
- The normal Studio flow does not expose skill names, installation steps, or a separate skill-start action.
- If automatic provisioning cannot recover, Studio reports that creative setup failed and keeps technical diagnostics behind progressive disclosure.
- Because `grill-with-docs` is marked `disable-model-invocation: true`, Fulcrum's workflow controller invokes it directly in response to the user's project-start action; the model does not decide to invoke it on its own.

### Interview behavior

- The skill maps the project as a design tree.
- Each round asks the whole current frontier: every unresolved decision whose prerequisites are settled.
- Every question includes Fulcrum's recommended answer.
- Answers reshape the tree and unlock later questions.
- Fulcrum researches facts it can discover; it asks the user to make decisions.
- There is no preset question or round limit.
- The user may pause, resume, or cancel. A time or cost ceiling may pause provider work, but it cannot remove unresolved branches or declare shared understanding.
- Interrogation ends only when the frontier is empty and the user confirms shared understanding.
- Visual-direction work cannot begin before the resulting Game Design Spec is approved.

### Documentation behavior

Domain Modeling records decisions while the interview proceeds:

- Resolved project language updates a project `CONTEXT.md` glossary.
- The glossary contains domain language, not implementation details or session notes.
- A decision receives an ADR only when it is hard to reverse, surprising without context, and the result of a real tradeoff.
- Ordinary preferences remain in the Game Design Spec or Visual Bible.

The project glossary is distinct from `SESSION_CONTEXT.md`, which is a local working-session handoff rather than project truth.

This replaces the one-round, five-question limit in `PRODUCT_SPEC.md` and moves interrogation-skill integration forward from the roadmap's later-expansion list. Those documents must be updated if this draft is approved.

## Creative artifacts and lineage

M1 preserves these outcomes without prescribing their internal TypeScript shape:

| Artifact                  | Purpose                                                                                |
| ------------------------- | -------------------------------------------------------------------------------------- |
| Interrogation state       | Resumes the design tree, rounds, answers, and current frontier.                        |
| Game Design Spec          | Records approved mechanics, scope, constraints, assumptions, and their origin.         |
| Project glossary and ADRs | Preserve shared language and qualifying design tradeoffs.                              |
| Visual directions         | Present meaningfully different interpretations of the approved game design.            |
| Visual Bible              | Stores the chosen direction as reusable visual tokens and human-readable guidance.     |
| Concept plan              | Proposes the specific images Fulcrum believes are needed and explains why each exists. |
| Concept set               | Records only the image revisions the user explicitly kept as one approvable package.   |

Every approved artifact is immutable and content-addressed. Revisions create descendants; they do not overwrite history.

### Visual tokens

The Visual Bible must express enough structured information for downstream prompt compilation, including:

- Style and prohibited styles
- Shape and silhouette language
- Palette and gameplay-signaling color roles
- Material and surface language
- Lighting and atmosphere
- Camera, scale, and readability constraints
- VFX language when relevant

The contract requires these meanings, not a final schema layout.

### Prompt inheritance

Concept prompts are compiled from approved revision references. Each concept records its ancestor hashes and the relevant visual tokens it received.

The user remains visibly involved in image generation:

- Fulcrum shows the proposed image subjects before ImageGen runs; it does not silently invent and select a hero, location, or threat.
- Confirming the concept plan authorizes those image-generation requests, not acceptance of their results.
- A generated image always begins in `needs review`; generation never selects a revision.
- Each required image receives its own dedicated review page with the complete, uncropped image at a useful inspection size.
- The review surface accepts a plain-English change request beside the current image.
- Fulcrum sends that request, the current image, the approved Game Design Spec, and only the relevant Visual Bible tokens to ImageGen.
- Previous and new revisions can each replace the full-size review canvas for inspection. The user explicitly chooses **Keep and continue**.
- Multiple images appear together only on the final concept-package summary, after each one has already passed detailed review.
- The concept set becomes approvable only after every required subject has one explicitly kept revision.

M1 must demonstrate that:

- A relevant direction change updates affected concept prompts.
- A preserved part of the direction remains unchanged.
- Unrelated project history is not sent to the image provider.
- No one manually copies creative prose from one stage to the next.

## Revision behavior

For the M1 acceptance run, use these safety rails:

- Present three visual directions.
- Allow one replacement of an unselected direction.
- Allow one focused change to the selected direction while preserving named aspects.
- Plan one to three concepts based on the brief.
- Allow one regeneration per concept before approval.

These are M1 proof bounds, not permanent limits for every future Fulcrum project.

A direction change invalidates only its descendants. Regenerating one concept leaves sibling selections untouched. Replaced revisions remain inspectable until the final concept set is approved.

## Human approvals

M1 has three high-leverage approval points:

1. **Game design:** the design tree is resolved, shared understanding is confirmed, and the Game Design Spec is approved.
2. **Visual direction:** one direction and its Visual Bible are approved.
3. **Concept set:** the exact selected revision for every required concept is approved as one set.

Replacement and change requests return to the current approval point; they do not invent new approval types.

## Studio experience

Studio should remain visually quiet and focused on the current decision:

- Show one Grill Me With Docs frontier round at a time.
- Compare directions with one large active visual and a compact filmstrip.
- Review concepts with one large active concept and simple slot navigation.
- Explain inherited visual tokens without exposing hidden reasoning.
- Keep provenance, hashes, and raw prompts behind progressive disclosure.
- Make pending, stale, blocked, rejected, and approved states unmistakable.
- State clearly whether an action can trigger another paid request.

Before durable implementation, create a replay-only browser prototype of the recommended focused flow plus two credible alternatives. Human review chooses the production interaction.

## Provider, cost, and recovery policy

M1 inherits M0's provider and safety seams:

- Every external request has a durable intent, idempotency key, retry limit, and budget decision.
- Ambiguous submissions are never repeated automatically.
- Generated images remain local immutable artifacts; workflow state carries references rather than image bytes.
- Credentials remain runtime configuration and never enter project truth, prompts, or logs.
- Restarting resumes the same interrogation, direction, or concept work.
- The default image route is the signed-in OpenAI subscription ImageGen capability used by Fulcrum's existing M0 subscription runner. It does not read an API key or issue a separately metered API request.
- Replay tests may use deterministic offline artifacts. User-facing acceptance prototypes use saved real ImageGen outputs, never CSS or procedural stand-ins presented as concept art.

The live M1 run requires explicit user authorization and a positive cap for any metered API route. Subscription routes still receive retry and elapsed-time limits. M1 does not require another paid image-to-3D job.

## Validation briefs

The acceptance matrix contains three brief shapes:

1. **Mechanics-first:** clear gameplay and camera, weak visual identity.
2. **Visual-first:** clear world and mood, incomplete playable loop.
3. **Constraint-heavy:** strong requirements with a material ambiguity or tension.

At least one brief differs from M0 in genre, camera, environment, and hero subject. At least one must require multiple Grill Me With Docs rounds.

## Acceptance criteria

### Product

- [ ] A clean Fulcrum environment provisions the Grill Me With Docs skill chain without user setup.
- [ ] Starting a project begins and persists the design tree, rounds, answers, documentation changes, and frontier.
- [ ] Each round asks the whole frontier and recommends an answer for every question.
- [ ] Discoverable facts are researched rather than delegated back to the user.
- [ ] Completion requires an empty frontier and explicit shared-understanding confirmation.
- [ ] The approved Game Design Spec records assumptions and their origin.
- [ ] Resolved terms update the glossary; only qualifying tradeoffs create ADRs.
- [ ] Three materially different visual directions can be compared and one approved.
- [ ] A focused direction change preserves the aspects the user pinned.
- [ ] The proposed image list is visible and editable before generation.
- [ ] No generated image is selected until the user explicitly keeps that revision.
- [ ] A plain-English change request edits the current image through subscription ImageGen and preserves both revisions for comparison.
- [ ] One concept can be regenerated without replacing its siblings.
- [ ] Concepts expose their approved ancestors and inherited visual tokens.
- [ ] The M0 replay path still reaches terminal completion.

### Durability and safety

- [ ] Restarting at any interrogation or approval point resumes the same revisions and selections.
- [ ] Restarting provider work reconciles existing submissions without duplicate spend.
- [ ] Revising an ancestor marks only affected descendants stale and deletes nothing.
- [ ] Existing M0 projects retain their artifacts, approvals, and terminal status.
- [ ] Ordinary tests are deterministic and offline.
- [ ] Secrets and image bytes are absent from workflow snapshots and project state.
- [ ] One explicitly authorized, budget-capped live run reaches an approved concept set.

### Quality

- [ ] All three validation briefs produce coherent, schema-valid creative artifacts.
- [ ] Explicit brief facts survive without semantic reversal.
- [ ] Material ambiguity is resolved rather than silently averaged away.
- [ ] Directions differ meaningfully while respecting gameplay and readability constraints.
- [ ] Compiled prompts contain relevant approved tokens and omit unrelated history.
- [ ] Type checks, tests, build, formatting, and browser inspection pass.

## Non-goals

M1 does not include:

- Multiview generation, deeper 3D quality work, Blender, rigging, or animation
- Asset dependency graphs or production-strategy classification
- New providers, runtimes, generated environment kits, or expanded Scene Spec behavior
- Gameplay implementation, autonomous refinement, or Gauntlets
- A general skill marketplace, collaboration, or remote artifact storage
- Open-ended conversation unrelated to the active design tree

## Implementation sequence

Each slice keeps Fulcrum runnable and the M0 replay path green.

1. **Interaction prototype** — compare the focused flow with two alternatives in the browser.
2. **Background skill runtime** — pin, provision, and verify `grill-with-docs`, `grilling`, and `domain-modeling` without adding user-facing setup.
3. **Project truth** — persist interrogation, documentation, selection, lineage, and invalidation state while preserving M0 projects.
4. **Shared understanding** — start Grill Me With Docs from the normal project workflow and approve the resulting Game Design Spec.
5. **Visual direction** — produce, compare, redirect, and approve multiple directions.
6. **Concept inheritance** — plan the concept set, compile prompts, regenerate one concept independently, and approve the set.
7. **Acceptance** — run offline checks, the varied-brief matrix, browser inspection, clean-environment automatic provisioning, and one authorized live run.

## Exit artifacts

M1 ends with:

- A durable multi-round design tree and approved Game Design Spec
- A project glossary and any qualifying ADRs
- Three purposeful direction revisions and one approved Visual Bible
- A demand-driven, approved concept set with visible inheritance
- Evidence of one focused direction change and one independent concept regeneration
- A green M0 regression and one approved live creative-to-concept run
- A short report covering cost, elapsed time, failures, and accepted limitations

## Approved proof bounds

1. Three directions are the M1 acceptance bound.
2. One replacement, one focused direction change, and one regeneration per concept are M1 safety rails.
3. The live M1 boundary is an approved concept set, with no new paid 3D requirement.
